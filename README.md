# Overload

A workout tracker. Log sessions, track measurements, set goals, watch your
numbers go up.

Originally a single self-contained HTML file with everything in browser
storage. It now has real accounts and server-side sync via Supabase, and ships
as an installable web app plus native iOS/Android shells through Capacitor.

---

## Before anything works: set up Supabase

This is the one step that can't be automated for you — it needs an account in
your name. Takes about five minutes.

1. Go to [supabase.com](https://supabase.com) and sign up (the free tier is
   plenty). Create a **New Project**: any name, set a database password and
   save it somewhere, pick the region closest to you.
2. Wait for it to finish provisioning (a minute or two).
3. Open the **SQL Editor** in the left sidebar, paste in the entire contents of
   [`phase1-schema.sql`](phase1-schema.sql), and run it. This creates the table
   your data lives in and turns on the security rules that stop one account
   reading another's data.
4. Go to **Project Settings → API** and copy two values:
   - **Project URL** — looks like `https://abcdefgh.supabase.co`
   - **anon public** key — a long string starting with `eyJ`
5. Paste both into [`docs/supabase-config.js`](docs/supabase-config.js).

> **On keys:** the `anon` key is designed to be public. It ships inside every
> Supabase web and mobile app, and the row-level security rules from step 3 are
> what actually protect your data. It's safe to commit.
>
> The **`service_role`** key is the opposite — it bypasses all security. Never
> put it in this project or anywhere else that reaches a browser.

### Worth knowing while you're testing

Supabase requires people to confirm their email address before they can sign
in. That means after registering you'll land on a "check your email" screen
rather than going straight into the app — this is correct behaviour, not a bug.

To skip it while developing, go to **Authentication → Providers → Email** and
turn off **Confirm email**. Turn it back on before real users exist.

## Running it

```bash
npm install
npm start           # serves the app at http://localhost:5173
```

You can leave `supabase-config.js` empty. With no keys the app runs in
**local-only mode** — everything stays in browser storage, exactly as the
original did, and a "Skip for now" button appears on the registration screen.
Useful for working on the interface without a connection.

## Tests

There's a mock Supabase server, so the cloud behaviour can be tested without
touching your real project or needing any keys.

```bash
# in one terminal
npm start

# local-only flow: gate, validation, registration, navigation, sign-out
npm run test:smoke

# cloud flow — needs the mock running in another terminal:
npm run mock
npm run test:cloud

# the confirm-email signup path (Supabase's default):
npm run mock:confirm
npm run test:confirm
```

`test:cloud` is the important one. It registers an account, changes a setting,
then **wipes local storage completely** before signing back in — so anything
that reappears can only have come from the server. That's the actual proof that
sync works.

All three exit non-zero on failure, and drop screenshots in `.smoke-shots/`.

## Putting it on a phone

**As a web app (no app store, no fees):** host `docs/` anywhere static —
Netlify, Vercel, Cloudflare Pages, GitHub Pages — open it on your phone and use
"Add to Home Screen". It installs, gets an icon, and works offline.

**As a real native app:**

```bash
npm run sync          # copy docs/ into the native projects
npm run open:android  # opens Android Studio
npm run open:ios      # opens Xcode
```

- **Android** needs [Android Studio](https://developer.android.com/studio).
- **iOS** needs a Mac with Xcode. There's no way around that for local builds —
  Apple only allows iOS builds on macOS. Cloud build services exist if you
  don't have one.
- Publishing costs $25 one-off for Google Play and $99/year for Apple.
- Change `appId` in `capacitor.config.json` from `com.overload.app` to
  something you control before submitting to either store.

## Layout

```
docs/                   the app — open this to understand anything
  index.html            all of it: markup, styles, logic
  supabase-config.js    your keys go here
  vendor/supabase.js    Supabase client, vendored (no build step)
  sw.js                 service worker, for offline
phase1-schema.sql       the table the app currently uses  ← run this
schema.sql              the fuller relational design (Phase 3, not yet used)
capacitor.config.json   native app settings
android/  ios/          native projects, generated by Capacitor
tools/                  icon generator, mock server, tests
CLAUDE.md               the original migration brief
```

There is **no build step**, and that's deliberate — the original app's
no-framework, no-bundler character is worth keeping. `docs/` is served as-is.

## How the data layer works

Worth understanding before changing anything here.

All persistence goes through three functions in `index.html` —
`loadState`, `saveKey` and `deleteKeySafe`. Every one of the app's ~48 save
sites calls `saveKey`/`debouncedSave`, so those three functions are the entire
storage surface.

They are **local-first, on purpose**:

> Writes land in `localStorage` synchronously first, then push to Supabase in
> the background. This is a gym app and gyms have terrible signal. A set you've
> just ticked off must never be lost to a failed request, so the network is
> treated as a replica — not as the source of truth for the session in progress.

Failed pushes go into a `dirty` set that survives a reload, and are retried on
reconnect, on app resume, and on a timer. When loading, a dirty key's local copy
always wins over the server's, so unsynced offline work is never overwritten by
stale server data. The cache is namespaced per account, so two people signing in
on the same phone can't see each other's data.

Please don't collapse this back into plain awaited network writes — it would
quietly reintroduce losing-your-sets-in-a-basement.

A small dot appears top-right when writes are pending (amber) or failing
(red), and is invisible when everything is synced.

### Personal records are computed, never stored

The app recalculates best-ever weight, 1RM, volume, reps, duration and distance
from full history whenever it needs them (`getBests`, `computeSessionPRs`).
Keep it that way. A cached PR table drifts out of sync with the data it
summarises, and then you have two answers to the same question.

## What's next

Phase 1 (real accounts, cloud sync) is done. Phase 3 migrates storage from the
current one-row-per-state-key layout in `phase1-schema.sql` to the proper
relational tables in `schema.sql` — `workouts` → `workout_exercises` → `sets`.

That matters most for `history`, which grows forever and currently gets
rewritten wholesale on every change. The small, rarely-changing slices
(settings, goals, measurement fields) are fine as they are.
